# التصميم التقني 0.2

## القرار الحالي

PHP 8.2+، HTML/CSS/JavaScript، Node.js 22+ مع SDK الرسمي، JSON محلي للمهمات، MP4 محلي. الواجهة تخاطب PHP فقط؛ مفتاح Runway لا يذهب إلى JavaScript. مجلد الويب `public`.

PHP يخاطب خدمة Node على `127.0.0.1:8787`. الخدمة تستعمل `@runwayml/sdk`، والمزود: `https://api.dev.runwayml.com`، إصدار `2024-11-06`. SDK يدير إنشاء المهمة وانتظارها؛ لا توجد حلقة استطلاع مزود مخصصة في PHP. النموذج `gen4.5`، المدة 5 افتراضيًا، النسبة `720:1280`. لا نغير الإعدادات بناءً على نص المستخدم حاليًا؛ إعداد التطبيق هو المرجع.

## العقود الداخلية

### إنشاء — `POST generate.php`

رأس `X-CSRF-Token` من الصفحة. جسم JSON:

```json
{
  "prompt": "وصفك",
  "request_id": "32 حرفًا سداسيًا ينتجها المتصفح"
}
```

رد نجاح القبول 202، أو 200 عند استعادة المعرف نفسه. يعيد `id`, `status`, `provider_task_id` مع بيانات العرض. المعرف المحلي عشوائي 128-bit، مستقل عن رقم Runway.

يرفض وصفًا فارغًا أو أطول من 1000 وحدة UTF-16، ومعرفًا غير صالح، وجلسة لديها عملية نشطة. قفل جلسة PHP وتسلسل حفظ الطلب، مع قفل ملف SDK ذري بـ wx وخريطة مهام نشطة في الخدمة، يمنعان إعادة إرسال المعرف نفسه. القفل يبقى بعد إعادة تشغيل الخدمة.

يسجل الحالة قبل الإرسال ولا يكرر POST تلقائيًا. SDK مضبوط على maxRetries: 0. رفض صريح من المزود بـ 4xx، عدا 408، يصنف فشلًا؛ انقطاع الاتصال و5xx أو رد قبول غير صالح يصنف إرسالًا غير مؤكد. سجل الجلسة يثبت قبل بدء الشبكة. لا يثبت ذلك exactly-once على مستوى المزود.

### متابعة — `GET status.php?id=LOCAL_ID`

يتحقق من ملكية الطلب داخل الجلسة ويقرأ سجل JSON فقط. يسأل /active في الخدمة المحلية للتأكد من وجود العامل. عند توقف الخدمة يحتفظ بمعرّف المزود ويتيح الاستئناف. حالات التوقف المعروضة دون كتابة فوق سجل العامل تمنع تعارض تحديثات PHP وNode.

### استئناف — `POST resume.php`

جسم JSON يحتوي id المحلي، مع CSRF وملكية الجلسة. يرفض المهمة دون معرّف مزود أو المهمة النهائية. يستدعي العامل `tasks.retrieve(providerId).waitForTaskOutput()` للحصول على نتيجة المهمة نفسها؛ لا يستدعي create. يسترجع رابطًا جديدًا عند فشل الحفظ إذا بقيت النتيجة لدى المزود.

### عامل SDK — `sdk/service.mjs`

يعرض /health و/active و/start و/resume على loopback فقط، ويرفض Origin وHost غير المحلي. لا ينفذ /health أي اتصال بالحساب. يستقبل المفتاح من PHP دون حفظه. يربط waitForTaskOutput قبل انتظار رد إنشاء المهمة ثم يحفظ رقمها. مهلة الانتظار عشر دقائق. يبقى التطبيق في PENDING أثناء انتظار SDK؛ لا يعرض تقدمًا مزعومًا. المهام الناجحة تنتقل إلى SAVING ثم READY، حتى بعد إغلاق الصفحة طالما الخدمة تعمل.

لا يُكتب الرابط الموقع في سجل المهمة ولا يُعاد للمتصفح. Node يستدعي `tools/save-video.php` مع الرابط على stdin، ومسار MP4 مشتق من المعرّف المحلي؛ أداة CLI لا تتلقى المفتاح. لا يوجد تشغيل تلقائي للخدمة بعد إعادة تشغيل الجهاز؛ المستخدم يشغل npm start ويستأنف المهمة المعروفة.

### مشاهدة وتنزيل — `GET/HEAD media.php?id=LOCAL_ID`

يقبل ملفًا محليًا حالته `READY` فقط، ويتحقق من جلسة مالكه. يدعم HTTP 206 لنطاق واحد و416 للنطاقات غير الصالحة، ويعيد `video/mp4`. `download=1` يضيف `Content-Disposition: attachment`.

## سجل المهمة

يشمل المعرّف المحلي، تجزئة جلسة المالك، الوصف، النموذج، المدة، المقاس، وقت البدء، حالة المهمة، معرّف المزود عند توفره، وقت الحفظ عند النجاح، و`api_cost_actual: null`. يحفظ `api_cost_credits` من cost.credits إن أعادته نتيجة SDK، وإلا يبقى null؛ لا يتحول هذا تلقائيًا إلى مبلغ فاتورة.

لا يسجل المفتاح أو الرابط المؤقت في المهمة. لا يرسل `owner` للمتصفح. لا يوجد تشفير للسجلات المحلية؛ هي تحت سيطرة جهاز المستخدم وليست مخزنًا متعدد المستخدمين.

## تنزيل MP4

يأخذ الرابط من نتيجة المزود فقط، ويتطلب HTTPS باسم نطاق. يرفض IP المباشر وبيانات المستخدم والمنفذ غير 443 والعناوين الداخلية والمحجوزة. يثبت عنوان IPv4 العام في cURL ولا يتبع إعادة التوجيه. يستعمل تحقق TLS الافتراضي، حد 100MB ووقت 120 ثانية، ويتحقق من توقيع `ftyp` الأساسي قبل تثبيت الملف. هذا ليس فحصًا شاملًا لكل محتويات الفيديو.

لا يرسل Authorization عند تنزيل ملف الوسائط. الرابط لا يظهر في الواجهة. يتم التنزيل إلى ملف مؤقت ثم تثبيت الاسم النهائي. خوادم لا تدعم IPv4 أو تعيد توجيهًا تحتاج معالجة متعمدة لاحقًا، وليس تعطيل الضوابط.

## حالات التطبيق

| الحالة | معناها |
|---|---|
| `SUBMITTING` | حفظ سجل قبل إرسال الطلب |
| `SUBMISSION_UNKNOWN` | تعذر تأكيد الإرسال؛ تحتاج مراجعة لوحة Runway |
| `PENDING` | SDK ينتظر نتيجة المهمة؛ حالات المزود الداخلية يتابعها SDK |
| `NEEDS_REVIEW` | توقف الانتظار أو العامل؛ استرجاع نفس رقم المزود |
| `SAVE_FAILED` | فشل تنزيل نتيجة ناجحة؛ استرجاع الرابط وإعادة الحفظ |
| `SAVING` | المزود نجح ونحفظ ملفه |
| `READY` | MP4 محفوظ محليًا |
| `FAILED`, `CANCELLED` | حالة نهائية بدون ملف جاهز |

يقرأ التطبيق أيضًا CANCELED من سجلات 0.1 القديمة كحالة نهائية، لكن SDK يستعمل CANCELLED الصحيحة. لا يوجد أي إجراء إلغاء جديد في الواجهة.

## ما الذي يتغير عند التوسع؟

طبقة `VideoProvider` بواجهات generate/edit/status لكل مزود، `DirectorService` لفهم الطلب، `EditRouter` لتوجيه محلي أو توليدي، `ComposerService` لـ FFmpeg، `StorageService` لتخزين دائم، Jobs بالخلفية. تفاصيل هذه الطبقات تُبنى عند مراحلها، ولا توجد حاليًا كودًا وهميًا في المنتج.
